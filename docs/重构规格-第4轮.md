# 第 4 轮：代码重构（按板块拆文件）+ 分板块测试

用户 2026-09-22 定的顺序：「先重构代码，重构之后再来做渲染，然后再根据各个功能板块进行测试。
打包的话就要分功能板块进行测试，因为内存不够」。

按 skill `modular-app-iteration` 的规矩：**不做真插件包**（物理上仍是一个 APK）、
**可以拆文件**（一件事一个文件、一个渲染器一个文件 + 一份登记表）、**只编只测改动的那部分**。

## 3. 板块与功能登记（`registry.js`）

6 个板块：随笔 / 渲染 / 存储 / 导出 / 设置 /（计划中）同步；23 个功能条目，其中 21 个已实现、
2 个计划中（随笔独立目录、WebDAV）。登记表是唯一数据源：界面、自检、测试映射都读它。

规矩（照 skill）：`planned` 的功能**不许出现在界面上**；`status=done` 的必须有 `testId`（静默时也在 DOM 里）
与 `test`（对应 `tools/boards/<板块>.sh#功能`）。

## 4. 分板块测试（内存不够，就一轮只跑一个板块）

| 命令 | 作用 |
|---|---|
| `bash tools/verify-board.sh list` | 列出板块与功能数（不碰设备） |
| `bash tools/verify-board.sh <板块> [--keep]` | 起模拟器 → 装包 → 跑**一个**板块的验收；默认跑完停掉模拟器回收内存 |
| `bash tools/verify-board.sh all` | 依次跑全部板块（**串行**），最后停模拟器 |
| `python3 tools/check_coverage.py [--strict]` | 文件层面覆盖自检（登记 vs 测试脚本是否存在） |
| （界面里）`window.__coverage` | 页面自检：没归属/空集合/界面空集合/没挂上/没测/未做 |

脚本里的三条纪律（都是踩过的坑）：
1. 每组开头 `refocus_app`：**自己导航到固定状态**，并把 devtools 转发重挂（点过链接/分享后
   应用可能被系统杀掉，探针会以 undici 报错的形式失败，看起来像功能坏了）；
2. `PATH` 里必须有 `~/.local/bin`（node 在那儿，缺了探针会静默变空值 → 一片假红）；
3. 断言只读「事实」：文件字节（`cat` 回宿主再判，设备上 `grep 中文` 会假阴性）、SQLite、DOM 几何、窗口焦点。

模拟器侧的两个环境坑：启动后可能撞 nexuslauncher 的 ANR 抢焦点（`am force-stop` 掉再 dump）；
2GB 内存下 Chrome 常驻会把应用挤掉（`refocus_app` 顺手 force-stop 浏览器）。
